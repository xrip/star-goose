# Star Goose — читаемая byte-exact реконструкция, v2

Ассемблерная основа для последующего C-порта игры из предоставленного `goose.zip`.

**Основной исходник: `src/GOOSE.asm`.** Он подключает 21 модуль кода в исходном порядке EXE. Все 204 найденных входа получили осмысленные имена и русские контракты: назначение, входы, эффекты, ограничения переноса. Некоторые входы — общие хвосты или части одной процедуры, а не независимые C-функции.

## С чего читать

Начните с [`docs/ARCHITECTURE_RU.md`](docs/ARCHITECTURE_RU.md), затем [`src/include/entity.inc`](src/include/entity.inc), [`src/code/01_boot_and_attract.asm`](src/code/01_boot_and_attract.asm), [`src/code/06_entity_pool.asm`](src/code/06_entity_pool.asm), [`src/code/09_entity_dispatch.asm`](src/code/09_entity_dispatch.asm) и [`src/code/10_player_surface.asm`](src/code/10_player_surface.asm).

Полный индекс с контрактами: [`docs/FUNCTIONS_RU.md`](docs/FUNCTIONS_RU.md). Форматы данных: [`docs/DATA_LAYOUT_RU.md`](docs/DATA_LAYOUT_RU.md). Порядок и ловушки C-переноса: [`docs/PORTING_TO_C_RU.md`](docs/PORTING_TO_C_RU.md). Неустановленные детали: [`docs/OPEN_QUESTIONS_RU.md`](docs/OPEN_QUESTIONS_RU.md).

## Что изменено относительно первой реконструкции

Код разнесён по подсистемам; адресные `sub_XXXX` заменены рабочими именами. Поля сущностей выражены через `E_X`, `E_Y`, `E_FRAME`, `E_HANDLER` и другие константы. Глобальные адреса отделены от полей структур: прежнее `[si+D_msg_insufficient_ram]` было смещением поля `+7`, а не обращением к строке сообщения. Для установленных стековых интерфейсов введены имена аргументов. Комментарии объясняют алгоритмы, побочные эффекты, владение стековым кадром и отличия 8/16-битной арифметики от обычного C.

В данных выделены 39 изменяемых шаблонов Entity, 29 наборов кадров, 24 части карт, таблицы звука и скалярные переменные. RLE карты записан понятными `MAP_RUN tile, count`, но **каждый исходный токен сохранён**, без повторного сжатия. Неустановленные данные не выданы за расшифрованные: их байты явно сохранены в отдельных диапазонах.

418 символических DS-смещений включают и самостоятельные объекты, и aliases внутренних полей; это не 418 независимых глобальных переменных.

## Сборка и проверка

Нужны Python 3.10+ и x86 GNU binutils (`as`, `objcopy`). Проверено на GNU binutils 2.44. Используется GNU as, Intel syntax, `.code16`, **не NASM/MASM**.

```sh
python3 build.py --reference ../goose.zip
```

Без оригинального архива:

```sh
python3 build.py
```

Оригинальный EXE нужен только для дополнительного прямого сравнения; исходники его не включают и не читают. Результат `build/GOOSE.EXE` имеет 53 684 байта, SHA-256:

```text
631ffed20bb29e564b455d9185220d30dc1c35964bd9f7aeb421cad4567c4a0b
```

Сборка проверяет весь хеш и отдельно все 6 022 исходных кодирования инструкций, заголовок, четыре DOS-релокации и исходные ресурсы. Файл `build/verification.json` содержит проверку текущей сборки. Результаты дополнительных проверок — `analysis/VALIDATION_V2.json`.

Без Python, **из корня проекта**:

```sh
as --32 -o build/goose.o src/GOOSE.asm
objcopy -O binary -j .text build/goose.o build/GOOSE.EXE
```

В Windows предусмотрен `build.cmd`; `py -3 build.py` также принимает `--assembler` и `--objcopy` с полными путями. Проверка нативной Windows-сборки не проводилась; Linux/WSL — путь с проверенным в этой работе инструментарием.

### Один самодостаточный файл

```sh
python3 tools/export_flat.py
as --32 -o build/flat.o dist/GOOSE.flat.asm
objcopy -O binary -j .text build/flat.o build/GOOSE.FLAT.EXE
```

`dist/GOOSE.flat.asm` — экспорт этих же модулей, не второй редактируемый источник истины. Его можно собрать из отдельной папки без include-файлов.

### Проверки для сопровождения

```sh
python3 tests/test_project.py
```

Проверяются навигационная карта инструкций, все границы и имена входов, форматы Entity/FrameSet, повторяемость RLE и итог модульной/одиночной сборки. Небольшие C-модели в `port/` проверяются отдельным `tests/test_c_models.py`; это **не готовый C-порт** и не доказательство эквивалентности всего игрового цикла.

## Важные ограничения

Имена и комментарии восстановлены анализом, а не получены из авторских исходников. Побайтовая тождественность не доказывает каждую семантическую гипотезу: визуальные названия объектов, некоторые state-поля и неразмеченные данные требуют дальнейшего разбора. Полный запуск игры, прохождение уровней и аппаратные тайминги не проверены.

Размеры и порядок инструкций не менялись. Не вставляйте новые `CALL/RET`, не переносите байтовые блоки и не добавляйте alignment ради «красивых функций»: это разрушит byte-exact базу. DS:0000..0005 по-прежнему перекрывают конец кода. `{load}`, `{disp16}`, `ACC16` сохраняют исходные кодирования и не являются мусором дизассемблера.

Для намеренно изменённого бинарника есть `python3 build.py --no-verify`; такой результат уже не заявляется byte-exact. Для C-порта лучше сохранять этот проект как неизменяемый эталон, а C-код развивать отдельно.
